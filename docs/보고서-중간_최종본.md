## 프로젝트 요약 (Abstract)

VisionVoice는 시각장애인이 음성 명령만으로 웹 페이지를 이해하고 실제 조작까지 수행할 수 있도록 설계된 AI 기반 웹 에이전트 시스템입니다.

1학기(3-2)에는 Chrome Extension, 로컬 FastAPI 서버, Google Colab 상의 Qwen2-VL-7B 멀티모달 모델로 구성된 단일 턴(single-turn) 파이프라인을 구현하여 국내 주요 웹사이트에서 **평균 65%의 임무 성공률과 30.7초의 응답 속도**를 기록하였습니다.

2학기(4-1) 중간 시점에는 (1) 1학기 실패 원인 심층 분석을 통해 모드 혼동(42.9%)과 좌표 정밀도(42.9%)가 주된 병목임을 규명하였고, (2) Computer-Use Agent 분야의 최신 동향(Qwen3-VL, UI-TARS-2, OmniParser V2 등)을 조사하여 오픈소스 기반 새로운 아키텍처로 **OmniParser V2 + Qwen3-VL-8B + Qwen-Agent (MCP)** 조합을 선정하였으며, (3) 학교 제공 NVIDIA DGX Spark(GB10) 환경으로 이식하여 PyTorch/Transformers/CUDA 호환성 이슈를 해소하고 Qwen3-VL-8B의 로컬 추론 검증을 완료하였습니다.

Phase A 초기 미니 벤치마크(합성 이미지 10개 시나리오) 결과 **임무 성공률 100%, 평균 응답 속도 9.3초**로, 1학기 대비 응답 속도 약 3.3배 향상 및 모드 혼동 0건을 확인하였으며, 이는 모델 업그레이드 방향성을 뒷받침하는 결과입니다.

잔여 학기에는 ① OmniParser V2와의 통합 파이프라인 구축, ② 실제 웹사이트 기반 평가 데이터셋 구축, ③ MCP 기반 Tool 확장(파일시스템·이메일), ④ QLoRA 기반 한국어 웹 특화 Fine-tuning을 수행하여 실사용 가능한 수준의 시각장애인 보조 에이전트 완성을 목표로 합니다.

## 1. 프로젝트 개요 (요약)

웹 접근성 조사에 따르면 상위 웹사이트 상당수가 WCAG 기준을 충족하지 못해(2025년 기준 94.8%), 시각장애인은 온라인 쇼핑, 행정 서비스, 학사 시스템 이용에서 지속적인 불편을 겪고 있습니다. 기존 스크린리더는 접근성 트리와 키보드 포커스에 의존해 텍스트를 순차적으로 낭독하기 때문에, 이미지·그래픽·동적 UI가 많은 국내 웹 환경에서는 핵심 정보와 버튼 위치를 파악하는 데 어려움이 있습니다.

VisionVoice는 이러한 문제의식에서 출발해, "화면을 보고 이해하며 실제로 행동까지 수행하는 AI 스크린리더"를 목표로 하는 웹 에이전트 프로젝트입니다. 사용자는 단축키(Ctrl+Shift+S)로 음성 인터페이스를 켜고 "이 화면 설명해줘", "검색창에 무신사 입력해줘", "아래로 내려줘"처럼 말하면, 시스템이 화면 스크린샷과 DOM 텍스트를 분석해 적절한 행동을 수행하고 그 결과를 음성으로 피드백합니다.

1학기에는 Chrome Extension–로컬 FastAPI–Colab Qwen2-VL 기반 에이전트를 연동한 단일 턴 MVP를 구현하여, 국내 웹사이트에서 단일 명령에 대한 화면 요약과 단일 행동 수행을 지원하는 수준까지 도달하였습니다.

2학기 중간 시점에는 1학기 모델(Qwen2-VL-7B)이 전문 GUI grounding 벤치마크(ScreenSpot-Pro)에서 2% 미만의 성능을 보이는 구조적 한계를 확인하고, 2025년 하반기 이후 출시된 최신 오픈소스 모델들과 Microsoft OmniParser V2를 결합한 신규 아키텍처로 전환하는 작업을 진행 중입니다. 또한 학교 제공 NVIDIA DGX Spark 로컬 환경으로 추론 서버를 이식하여 Colab·ngrok 의존도를 제거하고, 향후 상용 서비스와 Fine-tuning을 위한 기반을 마련하였습니다.

## 2. 목표 및 필요성

### 2.1 프로젝트 목표

본 프로젝트의 목표는 일반 사용자용 브라우저 에이전트(OpenAI Atlas 등)나 Computer-Use Agent(OpenCUA, UI-TARS 등)에서 보여준 웹 자동화 기술을 **시각장애인 접근성에 특화된 보조공학 도구로 재설계**하는 것입니다.

- 시각장애인이 음성 명령만으로 웹을 탐색·조작할 수 있도록, 음성 → 화면 이해 → 행동 수행 → 음성 피드백이 하나로 이어지는 능동형 스크린리더 구현
- 전맹 사용자를 위한 음성 중심 인터페이스와 저시력 사용자를 위한 관심 영역 하이라이트·확대·시각적 인디케이터를 동시에 지원하는 하이브리드 접근성 UX 설계
- 멀티모달 LLM이 생성한 좌표·행동 결과 위에 DOM 분석·점수 기반 요소 선택·Input fallback·Smart Scroll을 결합한 하이브리드 그라운딩 계층을 얹어 행동 신뢰도를 확보

**2학기(4-1) 추가 목표**

- 1학기 범용 VLM(Qwen2-VL-7B)의 구조적 한계를 극복하기 위한 최신 Computer-Use Agent 모델 이식 및 벤치마크
- Google Colab 의존성 해소 및 학교 제공 DGX Spark 로컬 환경 완전 이식
- 브라우저 외 로컬 파일·이메일 등으로의 Tool 확장 (MCP 기반)
- 한국어 웹 환경 특화 데이터셋 기반 Fine-tuning을 통한 성공률 향상

최종 달성 목표는 ① 단일 음성 명령에 대한 화면 요약 및 다단계 행동 수행, ② 국내 대표 웹사이트에서의 실사용 가능한 성공률 확보, ③ 한국어·접근성 특화 Fine-tuning과 MCP 기반 Tool 확장을 완료한 실사용 단계 에이전트의 완성입니다.

### 2.2 필요성 (배경 및 기존 기술의 한계)

WebAIM Million 등 조사에 따르면 상위 100만 웹사이트 중 94.8%가 색 대비 부족, 대체 텍스트 누락, 폼 레이블 미설정 등 접근성 문제를 안고 있으며, 이는 시각장애인의 기본적인 정보 접근을 가로막는 요인으로 작용합니다. 특히 ARIA 속성을 사용한 페이지가 미사용 페이지보다 오히려 오류가 2배 많다는 조사 결과는 기존 HTML/ARIA 의존 스크린리더 접근이 근본적 한계에 도달했음을 시사합니다.

기존 스크린리더(NVDA, JAWS, VoiceOver, TalkBack 등)는 접근성 태그가 잘 달린 사이트에서는 충분히 동작하지만, 동적 UI·이미지 중심·ARIA 미흡 사이트에서는 효과적으로 작동하지 못합니다. 사전 인터뷰에서 저시력 사용자는 스크린리더보다는 화면 확대·고대비·다크 모드 등 시각적 기능에 의존하며, 복잡한 페이지에서 결제·수강신청 같은 핵심 버튼을 찾지 못해 작업을 포기하는 경우가 있다고 응답하였습니다. 또한 "모든 내용을 길게 읽어주는 것"보다 결제 버튼 위치·가격·핵심 정보를 짧게 요약해 주는 방식을 선호하고, 필요한 영역만 강조·확대해 주는 시각적 보조를 병행하기를 원하였습니다.

한편 OpenAI Atlas·OpenCUA·UI-TARS 등 브라우저 에이전트 및 Computer-Use Agent 기술은 탭 열기·양식 작성·검색 등 일반 사용자의 작업 자동화를 목표로 설계되어 있으며, 시각장애인의 인지 부하·설명 가능성·실패 시 안전한 복구 전략은 핵심 요구사항이 아닙니다. 또한 2026년 출시된 GPT-5.4, Claude Computer Use, Gemini 2.5 Pro Computer Use 등 상용 모델들은 스크린샷 기반 고성능 조작이 가능하나, 다음과 같은 이유로 시각장애인 보조 도구에는 부적합합니다.

| 요인 | 상용 Computer-Use API의 문제점 |
|---|---|
| 개인정보 | 사용자 스크린샷(로그인·금융·의료 정보)이 외부 서버로 전송 |
| 비용 | 사용자당 월 수만원 단위 API 비용으로 SaaS 모델 지속 불가 |
| Fine-tuning | 1학기 멘토링 권장 사항인 Fine-tuning 수행 불가 |
| 재현 가능성 | 졸업작품 오픈소스 공개 요구와 상충 |
| 접근성 인증 | 공공기관·의료 접근성 인증에서 결격사유 |

VisionVoice는 이러한 기술적·정책적 제약을 모두 고려하여, **오픈소스 모델의 로컬 구동 + Fine-tuning + Tool 확장**이라는 현실적이면서도 기술 최전선을 따라가는 방향으로 설계되었습니다.

### 2.3 사회·기술·산업적 의의

**사회적 의의**: VisionVoice는 시각장애인의 웹 접근성을 실질적으로 향상시켜, 온라인 쇼핑·공공서비스 신청·학사 행정·예약 등 일상적인 디지털 업무를 주변 도움 없이 스스로 처리할 수 있는 가능성을 높입니다. 이는 가족·보조인력에 대한 의존도를 줄이고, 교육·고용·여가 등 다양한 분야에서 시각장애인의 참여 기회를 확대하는 데 기여할 수 있습니다.

**기술적 의의**: 멀티모달 LLM을 실제 브라우저 환경에 결합해 화면 스크린샷·DOM 텍스트·음성 명령을 통합적으로 처리하는 Computer-Use Agent를 구현하고, 모델 출력 위에 하이브리드 그라운딩 계층을 더해 행동 신뢰도를 높인 점에서 의의를 가집니다. 2학기에는 여기에 Microsoft OmniParser V2의 스크린샷 구조화 파싱, Qwen3-VL-8B의 네이티브 MCP·Tool use 지원, QLoRA 기반 경량 Fine-tuning을 결합하여 **완전 오픈소스 기반 접근성 특화 에이전트**라는 새로운 기술 조합을 제시합니다.

**산업적 의의**: 접근성 기술을 단순 낭독 보조 기능에서, 웹 자동화·개인 비서·교육·헬스케어 등 다양한 도메인에 적용 가능한 장애인 특화 브라우저 에이전트로 확장하는 시도를 보여줄 수 있습니다. 상용 API 기반이 아닌 **로컬 구동형 개인 정보 보호 SaaS** 모델은 공공기관·의료·금융 등 민감 정보를 다루는 도메인에서 경쟁력을 가지며, 웹 접근성 인증 의무화 흐름과 맞물려 B2B·B2G 시장 기회를 확보할 수 있습니다.

## 3. 세부 개발 내용 및 방법

### 3.1 전체 시스템 구조

#### 3.1.1 1학기 MVP 구조 (완료)

```
Chrome Extension (Frontend)
  ├─ content.js  : 마이크 녹음, DOM 추출, 액션 실행, 시각적 피드백
  └─ background.js : 스크린샷 캡처, 통신 중계, TTS 출력
          ↓ [Audio + Screenshot + DOM]
Local FastAPI Server (CPU)
  ├─ Faster-Whisper (int8) : 한국어 STT
  └─ Colab 중계 로직
          ↓ [Image + DOM + Goal]  (ngrok tunnel)
Google Colab AI Server (T4 GPU, 무료)
  └─ Qwen2-VL-7B + 4-bit Quantization
        → Action JSON 생성 (bbox, type, text_content, speech)
```

Chrome Extension ↔ Local 간 ngrok 터널 1개, Local ↔ Colab 간 ngrok 터널 1개, 총 2개의 터널을 통해 연결됩니다.

#### 3.1.2 2학기(4-1) 확장 구조 (진행 중)

```
Chrome Extension (Frontend)
          ↓
Local FastAPI Server
  └─ Faster-Whisper STT
          ↓ [Image + Text Command]
DGX Spark Local AI Server (GB10 GPU, 학교 제공)
  ├─ OmniParser V2 (Microsoft)
  │    : 스크린샷 → 구조화된 UI 요소 리스트
  ├─ Qwen3-VL-8B (Alibaba)
  │    : 멀티모달 추론, 네이티브 Tool use
  └─ Qwen-Agent Tool Router (MCP)
        ├─ Web Agent (Chrome Extension 연동)
        ├─ Filesystem Tool (로컬 파일 읽기)
        └─ Gmail Tool (메일 발송)
```

주요 변경점은 (1) Google Colab 의존 제거 및 DGX Spark 로컬화, (2) OmniParser V2의 UI 구조화 파싱 단계 추가, (3) 범용 Qwen2-VL에서 GUI 특화 Qwen3-VL로 모델 업그레이드, (4) 브라우저 외 Tool 확장(MCP 기반)입니다.

### 3.2 1학기 구현 핵심 요약

#### 3.2.1 멀티모달 프롬프트 설계

Colab AI Agent의 핵심은 `agent_step(image, dom_text, user_goal)` 함수로, 사용자 요청과 상단 1200자 DOM 텍스트를 함께 제공하고 다음과 같은 엄격한 JSON 응답 스키마를 강제하였습니다.

- `intent`: "action" / "explain" / "answer" 중 하나
- `actions[].type`: "click" / "input" / "scroll" / "go_back" 중 하나
- `bbox`: 0~1000 정규화 좌표
- `text_content`: 화면에 보이는 실제 텍스트 (시각적 fidelity)
- 입력/검색 요청에는 `click` 대신 반드시 `input` 타입 + `value` 필드 사용

#### 3.2.2 하이브리드 그라운딩 및 행동 실행

멀티모달 LLM의 좌표 예측 오차와 실제 DOM 구조 간 불일치를 해결하기 위해 **AI 예측 bbox를 '탐색 범위'로만 사용하고, 실제 클릭 대상은 DOM 기반 스코어링 알고리즘으로 결정**하는 하이브리드 구조를 적용하였습니다.

스코어링 기준:
- Input Tag 매칭: +2000 (사용자가 '입력' 요청 시 최우선)
- Text 완전 일치: +500
- Box 내부 위치(IoU): +200
- Tag 유형 가점: +100 (a, button, input 등)

#### 3.2.3 자원·환경 제약 대응 (1학기)

무료 Colab T4 GPU 16GB에서 7B 모델을 구동하기 위해 다음 최적화를 적용하였습니다.

- **4-bit Quantization (BitsAndBytes NF4)**: VRAM 15GB → 5.5GB
- **Smart Resize (factor=28)**: 1920×1080 → ~1000×1000, ViT 패치 크기에 최적화
- **Colab–로컬 ngrok 이중 터널**: HTTPS–localhost 혼합 콘텐츠 차단 우회

#### 3.3.3 아키텍처 결정: OmniParser V2 + Qwen3-VL-8B + Qwen-Agent (MCP)

**선정 근거**
1. **완전 오픈소스**: API 비용 없음, 사용자 스크린샷이 외부 서버로 전송되지 않아 개인정보 보호 우수
2. **DGX Spark 완벽 구동**: 128GB unified memory로 bf16 정밀도 운용 가능 (양자화 불요)
3. **Fine-tuning 지원**: NVIDIA Developer Forum에 Qwen3-VL + DGX Spark + QLoRA 공식 가이드 존재
4. **MCP 네이티브**: Qwen-Agent 프레임워크로 별도 Router 구현 불요, 2학기 교수님 피드백(MCP 확장) 자연스럽게 해결
5. **GUI 특화 성능**: ScreenSpot 계열 벤치마크에서 Qwen2-VL 대비 수십 배 개선
6. **한국어 지원**: Qwen 계열은 한국어 학습이 충분히 반영된 오픈소스 중 최상위

### 3.4 2학기(4-1) DGX Spark 환경 구축 (7주차 수행)

1학기의 Google Colab·ngrok 의존 구조는 상용 서비스·Fine-tuning에 부적합하므로, 학교 제공 NVIDIA DGX Spark로 추론 서버를 이식하였습니다.

#### 3.4.1 하드웨어 및 초기 환경

- **GPU**: NVIDIA GB10 (Grace Blackwell Superchip, compute capability 12.1)
- **Memory**: 128GB Unified Memory (CPU-GPU 공유)
- **OS**: Ubuntu aarch64 (ARM64), CUDA 13.0, Python 3.10
- **접근**: SSH 전용, 팀 리더(조혜원) 계정에서 작업

#### 3.4.2 발견된 호환성 이슈 및 해결

DGX Spark의 ARM64 + Blackwell GB10 + CUDA 13 조합은 주류 ML 스택과 여러 호환성 이슈를 발생시켰습니다.

| 이슈 | 원인 | 해결 방안 |
|---|---|---|
| OpenCUA-7B 로딩 실패 (1학기 opencua_mvp 드랍 원인) | transformers 4.45에 `qwen2_5_vl` 모듈 부재 | transformers 4.57로 업그레이드 |
| transformers 5.x 시도 시 OpenCUA custom code 브레이크 | `tie_weights(recompute_mapping=...)` API 불일치 | 4.57 버전으로 고정 |
| bitsandbytes 4-bit 양자화 ARM64 미지원 | Blackwell 아키텍처 비지원 | **불요**: 128GB unified memory로 bf16 풀 정밀도 직접 구동 |
| PyTorch 2.9.0 inference 시 nvrtc 에러 | Blackwell GB10 (sm_121) 미지원 | PyTorch 2.11.0+cu128로 업그레이드 |
| `torch.prod()` JIT 컴파일 지속 실패 | nvrtc가 sm_121 대상 컴파일 불가 | `torch.prod`를 CPU 경로로 monkey-patch |
| HuggingFace Xet storage HTTP 416 에러 | Xet CAS 서버 일시 이슈 | `HF_HUB_DISABLE_XET=1` 환경변수 적용 |

#### 3.4.3 최종 설치 환경

- torch 2.11.0+cu128 (Blackwell 지원 확인)
- transformers 4.57.6
- qwen-agent 0.0.34 (MCP 통합용)
- faster-whisper 1.2.1, accelerate 1.13.0
- **모델**: Qwen3-VL-8B-Instruct (17GB), OmniParser V2 (1.1GB), Qwen2-VL-7B-Instruct (16GB, 백업)

## 4. 선행 기술 및 관련 연구

### 4.1 기존 스크린리더 및 웹 접근성 연구

NVDA, JAWS, VoiceOver, TalkBack 등 기존 스크린리더는 접근성 트리·ARIA·키보드 포커스 기반으로 설계되어, 정적 HTML 중심 사이트에서는 충분히 동작합니다. 그러나 WebAIM Million 조사 기준 94.8%의 웹사이트가 WCAG 기준을 미달하는 현실에서, 접근성 태그 의존적 방식은 구조적 한계를 갖습니다.

### 4.2 OpenCUA: Computer-Use Agent용 기초 모델

Wang et al. (arXiv:2508.09123, 2025)은 Qwen2.5-VL 기반 Computer-Use Agent 전용 모델을 제안하였습니다. VisionVoice 1학기에 opencua_mvp로 구현을 시도하였으나, `transformers` 버전 호환성 이슈로 드랍되었으며, 2학기 DGX Spark 이식 과정에서 원인이 규명되었습니다.

### 4.3 browser-use: 범용 브라우저 자동화 에이전트

GitHub 52,000+ stars의 오픈소스 프로젝트로, DOM 파싱 + 비전을 결합한 웹 자동화 에이전트입니다. 일반 사용자용 자동화를 목표로 설계되어 시각장애인 접근성 특화 요구사항(인지 부하, 실패 복구, 시각적 보조)은 고려되지 않았습니다.

### 4.4 Qwen3-VL 시리즈 (Alibaba, 2025.09~10)

Qwen2-VL의 후속 모델로 4B/8B/30B-A3B/235B-A22B 변종을 제공합니다. ScreenSpot에서 32B 모델이 95.8%, 235B 모델이 OSWorld 66.7%를 기록하며 오픈소스 최상위 성능을 보입니다. Qwen-Agent 프레임워크를 통해 MCP 프로토콜, 함수 호출, Chrome Extension 등을 네이티브로 지원합니다.

### 4.5 UI-TARS-2 (ByteDance, 2025.09)

GUI 조작 전용으로 훈련된 멀티모달 모델입니다. 2B/7B/72B 변종이 있으며, Online-Mind2Web 88.2%, OSWorld 50.6%로 Claude·OpenAI 에이전트를 능가하는 GUI 성능을 보입니다. 다만 한국어 지원 명시가 부족하여 VisionVoice의 1차 선택에서는 제외되었습니다.

### 4.6 OmniParser V2 (Microsoft)

스크린샷을 구조화된 UI 요소 리스트(bbox + 아이콘 유형 + 설명)로 변환하는 파서입니다. 모델이 아닌 전처리기 성격으로, 어떤 VLM과도 결합 가능합니다. icon_detect는 AGPL, icon_caption은 MIT 라이선스로, 본 프로젝트에서는 연구 목적 사용에 적합합니다.

### 4.7 MCP (Model Context Protocol, Anthropic)

AI 에이전트와 외부 도구(파일시스템, 이메일, DB 등) 간 표준 통신 프로토콜입니다. Qwen3-VL이 Qwen-Agent를 통해 MCP를 네이티브 지원하여, 본 프로젝트의 Tool 확장 요구사항을 자연스럽게 충족합니다.

### 4.8 VisionVoice의 차별성·혁신성

VisionVoice는 위 선행 기술들을 단순히 사용하는 것이 아니라, **시각장애인 특화 접근성 요구사항** 관점에서 재조합·재설계합니다.

| 구분 | VisionVoice 차별점 |
|---|---|
| vs 기존 스크린리더 | HTML/ARIA 의존 제거, 스크린샷 기반으로 접근성 미준수 사이트에서도 동작 |
| vs 범용 Computer-Use Agent | 시각장애인 인지 부하 최소화, 실패 복구 전략, 음성·시각 병행 피드백 |
| vs 상용 API | 완전 로컬 구동, 개인정보 외부 전송 없음, Fine-tuning 가능 |
| vs 단일 모델 접근 | OmniParser + VLM + MCP Tool Router 3중 구조로 신뢰성·확장성 확보 |

| 16 | 제출 | 최종 정량 평가, 최종 보고서·발표 자료·창업 플랜 완성 | 전원 |

### 5.2 확장 구현 목표 (우선순위별)

본 프로젝트는 4-1 학기 내에 모든 핵심 기능을 완성하는 것을 목표로 하며, Phase A~C 주요 과제 외에 다음과 같은 확장 기능을 학기 내 구현할 계획입니다. 구현 우선순위와 예상 배치는 아래와 같습니다.

**우선순위 1 — Tool 확장 전면화 (Phase B, 13주차)**

1학기 구조의 "브라우저 한정" 한계를 완전히 해소하기 위해, MCP 기반 Tool Router에 파일시스템·Gmail뿐 아니라 **Calendar Tool**까지 통합하여 일정 조회·등록까지 지원합니다. 세 가지 Tool은 Qwen-Agent의 표준 인터페이스를 통해 동일한 형식으로 등록되므로 구현 한계 비용이 크지 않습니다.

**우선순위 2 — Fine-tuning 정식 수행 (Phase C, 14주차)**

1학기 최아영 교수님의 권장 사항인 Fine-tuning을 본격 수행합니다. 경량 증명 수준이 아니라 **100~200개 한국어 웹 특화 샘플**을 확보하여 QLoRA 학습을 진행하고, 학습 전후 정량 비교를 수행합니다. DGX Spark 128GB unified memory는 Qwen3-VL-8B + QLoRA 학습을 bf16 또는 FP8 정밀도로 충분히 지원합니다.

**우선순위 3 — Multi-turn Agent 확장 (Phase C, 15주차)**

"검색하고 첫 번째 결과 클릭" 또는 "무신사에서 이 옷 사줘"와 같은 복합 명령을 1개 명령 = N개 액션으로 분해하여 순차 실행하는 **Multi-turn Agent**를 구현합니다. 실행 후 스크린샷을 재촬영하여 AI가 상태를 재확인하는 루프 구조를 설계하며, 이는 Qwen-Agent의 ReAct 스타일 실행 프레임워크를 기반으로 합니다.

**우선순위 4 — Dynamic Planning (Phase C, 15주차)**

페이지 응답이나 액션 실행 결과에 따라 **다음 액션 계획을 실시간으로 재조정**하는 기능을 추가합니다. 예를 들어 검색 결과 페이지가 예상과 달리 팝업을 먼저 띄우는 경우, 원래 계획된 "첫 번째 결과 클릭" 대신 "팝업 닫기 → 재시도"로 동적 전환합니다.

### 5.3 리스크 관리 및 우선순위 조정 원칙

10주 잔여 기간 내 상기 확장 목표를 모두 완성하는 것이 이상적이나, 실제 개발 속도·데이터 수집 가능 규모·DGX Spark 학습 안정성에 따라 우선순위가 조정될 수 있습니다. 조정이 필요한 경우 다음 원칙을 따릅니다.

1. Phase A 핵심(Qwen3-VL + OmniParser 통합)과 Phase B 핵심(평가 데이터셋, MCP Tool Router)은 **최우선 사수**
2. Fine-tuning은 **데이터 규모를 축소해서라도 증명 수준 실행** (최아영 교수님 권장 사항 이행)
3. Multi-turn / Dynamic Planning 중 시간 부족 시 **Multi-turn 우선** 구현 (Dynamic Planning은 설계 수준으로 대체)
4. Calendar Tool은 Filesystem·Gmail과 동일 인터페이스라 **시간 부족 시에도 최소 구현**

### 5.4 기대 효과 및 활용 분야

**기대 효과**
- 1학기 임무 성공률 65% → **80% 이상** 목표 (Phase A 초기 합성 테스트 100% 근거)
- 응답 속도 30.7초 → **10초 이하** 달성 (Phase A 초기 9.3초 확인)
- 브라우저 밖 시나리오(파일·이메일)까지 확장되는 **실사용 가능 수준의 시각장애인 비서**

**활용 분야**
- 공공기관·기업 웹사이트 접근성 플러그인 (B2B/B2G SaaS)
- 시각장애인 개인 사용자용 데스크톱 에이전트
- 교육·의료·공공서비스 분야 특화 Fine-tuning 버전 확장
